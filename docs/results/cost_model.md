# Abstract cost model: stage budgets

**This is an abstract cost model, not a WCET analysis.** Costs are artificial
weights on source-level operations (load, store, add, mul, branch). No processor,
cache, pipeline, or compiler is modelled. The numbers cannot be read as
durations, and they say nothing about any real platform.

Source: `fstar/src/Icarus.Cost.fst`. The cost table is generated by
`fstar/out/icarus_cost`, which is extracted from the same definitions the proofs
use. Reproduce it with `make fstar && ./fstar/out/icarus_cost`.

## Question

Do the per-stage budgets in `Icarus.Timing` (Acquire 120, Normalize 80,
Estimate 220, Decide 180, Control 160, Validate 90, Record 50; frame 1000) hold up
against the operations each stage actually performs, counted from the
implementations?

## Two weightings, two scan policies

- `unit`: every primitive costs 1.
- `heavy`: mul 3, load 2, store 2, branch 2, add 1. It exists to show that the
  conclusions depend on the weighting.
- `slots = 16`: each frame scans the whole fixed fault table. This is the
  implemented policy (`apply_faults` in `ats/src/sim.dats`, and likewise in the
  reference).
- `slots = 2`: a per-step cursor that touches only live rows. This is modelled
  only. No implementation uses it.

| Stage | Budget | unit/16 | unit/2 | heavy/16 | heavy/2 |
|---|---:|---:|---:|---:|---:|
| Acquire | 120 | **188** | 104 | **374** | **206** |
| Normalize | 80 | 24 | 24 | 48 | 48 |
| Estimate | 220 | **272** | **272** | **534** | **534** |
| Decide | 180 | 118 | 34 | **236** | 68 |
| Control | 160 | 76 | 76 | 152 | 152 |
| Validate | 90 | 32 | 32 | 64 | 64 |
| Record | 50 | 11 | 11 | 22 | 22 |
| **Frame** | 1000 | 721 | 553 | **1430** | **1094** |

Bold marks a cost over its budget.

## Machine-checked statements (unit model)

Each of these is an `assert_norm` in `Icarus.Cost` and is discharged by F\*:

| Statement | F\* name |
|---|---|
| Acquire with the full scan exceeds 120 | `scan_all_acquire_exceeds` |
| Acquire with the cursor fits in 120 | `cursor_acquire_fits` |
| Estimate as implemented exceeds 220 | `estimate_exceeds` |
| Estimate with (A − LC) merged fits in 220 (cost 212) | `merged_estimate_fits` |
| The saving equals exactly the innovation, C x̂, and its norm | `merged_saving_is_the_monitor` |
| Whole frame fits in 1000 under both scan policies | `frame_fits_scan_all`, `frame_fits_cursor` |
| matvec cost is monotone in both dimensions | `matvec_monotone` (general lemma) |

## Findings

1. **The per-stage budgets are not consistent with the implementation under the
   unit model.** Acquire (188 > 120) and Estimate (272 > 220) both exceed their
   allotments. The frame total (721) still fits. `Icarus.Timing.schedule_fits`
   proves only that the *budgets* sum to at most 1000. It says nothing about
   whether stage work fits its budget, and this model shows that in two stages it
   does not.
2. **The Acquire overrun is caused by the scan policy.** Scanning all 16
   fault rows costs 84 more than a 2-row cursor, which is the whole gap. In this
   model, an indexed fault schedule would fix Acquire.
3. **The Estimate overrun cannot be fixed for free.** The merged observer
   fits (212 ≤ 220), but only because it never forms the innovation y − C x̂. The
   estimator-disagreement monitor (`INNOV_THRESH`) reads exactly that quantity.
   F\* checks that the saving equals the innovation's cost. The model forces a
   choice between the 220 budget and the monitor.
4. **The heavy weighting reverses the frame-level conclusion** (1430 and 1094,
   both > 1000). Whether the frame fits is a property of the weighting, not of the
   design. No claim in this repository depends on either weighting being realistic.

## What this does not show

- Nothing about time on any real hardware.
- Nothing about the reference (Python) or the Idris/Lean executables. The
  operation counts follow the ATS frame loop and the reference algorithm. They
  were transcribed by hand, and no tool checks that transcription.
- The simulated overrun in the fixtures (`T` lines, `fault_overrun`) is injected
  directly as ticks. It is not derived from this model.
